## 1. マイルストーンごとに学んだこと

### M1 骨組み

- `CREATE TABLE IF NOT EXISTS` は既存のテーブルを黙って残す。後から足した制約（主キーの NOT NULL、CHECK）が、手元の古い DB には一度も効いていなかった。テストは毎回新しい DB で動くので気づけない。スキーマにバージョンを付け、古い DB は起動時に拒否するようにした（D26）
- Rancher Desktop のファイル共有は、変更がコンテナに届くまで約10秒遅れる。書き込み直後の検査が古い内容を読むことが何度もあった（K6）

### M2 登録

- 検証を「外せる」形にするには、作り方そのものを変える必要がある。challenge の行を Cookie で引くと、C5 の縛りが「行の取り出し方」に埋め込まれ、外して攻撃を再現できない。値で引いて C5 で比べる形に変えた（D21）。設計の段階では見えず、攻撃再現テストを書こうとして初めて気づいた
- 「どの検査が拒否したか」と「どの検査を外すと通るか」は一致しないことがある。challenge の二重使用は、C4 があると行が消えているので C2 で拒否され、C4 を外すと通る。攻撃シナリオに `rejectedBy` を別に持たせた
- `attestation: "none"` でも AAGUID がゼロになるとは限らない。1Password は自社の AAGUID を返した

### M3 ログイン

- L2（鍵の持ち主と `userHandle` のユーザーが一致）の意味は、セッションを誰に発行するかで変わる。仕様どおり `userHandle` のユーザーに発行すると、L2 を外したとき「自分の鍵 + 被害者の `userHandle`」で乗っ取れることを示せた（D28）
- L1（未登録の鍵の拒否）は外しても攻撃が通らない。後続の L2・L3 が保存済みの鍵を前提にしているから。「外しても別の検査が止める」という期待値（`withoutCheckRejectedBy`）を持たせた
- 検査と更新が別の文だと、間に別のリクエストが割り込める。A4（signCount）の条件を UPDATE 文に入れ、更新件数で判定する形にした。この「検査と記録を1つの操作にする」は、C4、S3、M7 の削除でも繰り返し使った

### M4 可視化

- 遅延デコードと検査の順序は、表示のコードにも効く。表示のために authenticatorData を先に読むと、C4 より前にデコードの例外が出て challenge が消費されない
- 検証の途中経過を見せる仕組みは、本番に残ると情報漏洩になる。既定は off にし、`production` との組み合わせは起動時に拒否した（D34、K5）

### M5 差分テスト

- `@simplewebauthn/server` は、challenge の期限・使い捨て・ブラウザとの結び付け、credential の登録状況と持ち主をアプリに任せている。L2 の攻撃は、ライブラリだけでは受理される。ライブラリを使えば安全、ではなく、ライブラリが何を見ていないかを知っておく必要がある

### M6 ステップアップ

- ステップアップでは、ユーザーが ceremony の前に分かっているので、確かめる相手が `userHandle` ではなくセッションになる（WebAuthn L3 §7.2 手順6）。ログインの L2 をそのまま使うと、`userHandle` を返さない認証器で正当な承認が落ちうる。S1 を別に立てた
- C5 を「ユーザー」に縛っていたため、漏れた応答を同じユーザーの別セッションで使えた（PR レビューで発見）。「セッション」に縛り直して初めて、C5 を外すと通る攻撃を再現できた。テストで「外すと通る」が示せない検証は、守る対象がずれていないかを疑う手がかりになる
- SQLite の `UPDATE ... RETURNING` は更新後の値を返す。計画どおりに書くと承認の照合が必ず失敗した。テストが赤くなって気づいた（D38）

### M7 複数パスキー

- M6 の時点で承認のハッシュに操作の種類（`kind`）を入れておいたので、追加・削除を検証項目を増やさずに同じ仕組みに載せられた（D42）
- 承認の状態をサーバーと画面の両方で持つと、ずれた瞬間に「認証器にだけ鍵が残る」という戻せない結果になる。状態は持ち主（サーバー）に聞く形に直した（D48）
- それでも、認証器での作成とサーバーへの保存は原子的にできない。複数タブや通信の失敗では残る（K12、D50）。防ぐことと、起きたときに消せることの両方が要る
- 仕様上「認証器の役目」とされていることは、製品によって守られたり守られなかったりした。1Password は `excludeCredentials` を守らず、Signal API での削除も反映されなかった（K11、K2）

## 3. 9章の残リスクへの考察

9章の表の行ごとに、PoC を作って分かったことを足す。

### 防げたもの

- **フィッシング・リプレイ**: origin と RP ID の照合（C3、A1）、challenge の使い捨てと要求元への紐づけ（C2、C4、C5）で、構造的に防げる。どれも「外すと通る」テストがある。ここはパスキーの本領で、追加の工夫は要らなかった
- **サーバー DB の漏洩**: 公開鍵しか持たないので、漏れてもログインには使えない。セッションもトークンの SHA-256 しか保存していないので（D27）、DB の中身だけではセッションを奪えない。9章の「セッションIDが漏れると悪用される」は、DB ではなく Cookie そのものが盗まれた場合の話になる

### 減らせたが残るもの

- **盗まれたセッションでの高リスク操作**: ステップアップで、送金・パスキーの追加・削除には、その場の署名が要る。承認は使った時点で S3 が消費するので、使い終わった承認は悪用できない。残るのは、承認したのに使われなかった承認（送金の取りやめ、追加の中断）が期限まで（最長5分）セッションに残り、その間にセッションを盗まれて、承認した内容のまま実行される場合と、ステップアップを要しない操作（残高や履歴の閲覧）。ログイン後のセッションそのものを端末に縛る仕組み（DBSC など）が次の手になる
- **攻撃者が追加した鍵**: 追加にもステップアップを付けたが、攻撃者が一度追加に成功すると、本人が鍵を消しても攻撃者の既存セッションは残る（D47）。本番では、鍵の削除時にそのユーザーの全セッションを失効させること、鍵の追加・削除を別経路（メールなど）で本人に通知することが要る
- **同期元の乗っ取り**: 実機で使った鍵は 1Password も Apple Passwords も BE=1・BS=1（同期型）だった（開発 DB の `credentials` で確認。docs/03 の M7 の結果）。保管庫が開かれれば鍵も使われる。PoC では記録と表示しかしていない（Q4 の結論は4章）

### WebAuthn だけでは防げないもの

- **画面改ざんによる誤承認**: 認証器は取引内容を表示しないので、改ざんされた画面で別の送金を承認させられる。WebAuthn の拡張である Secure Payment Confirmation は、ブラウザ自身が金額と支払先を表示してから署名させる仕組みとして説明されている。対応ブラウザの範囲は確かめていない（推測）
- **アカウント復旧**: PoC では作っていない。本番では「パスキーを失くした人をどう戻すか」が最弱点になる。M7 の複数パスキーは、復旧手段を増やす方向の対策になる
- **サーバーと認証器のずれ**: `excludeCredentials` も Signal API も、守るかどうかは認証器次第（K11、K2）。作成と保存も原子的にできない（K12）。サーバーの DB と認証器の中身はずれうるものとして扱い、利用者が一覧から鍵を消せることを前提にする

## 4. 持ち越した未決事項への結論

### Q3 ステップアップの有効期間（5分）

PoC では5分のまま変えない（D51）。ただ、使ってみて分かったことがある。

- 送金では、画面が承認の直後に自動で送り直すので、承認から使うまでは数秒だった。使った時点で S3 が承認を消費するので、5分の残りは悪用されない
- 期限が効くのは、承認したのに使われなかった場合（送金の取りやめ、追加の中断）。その承認は期限まで（最長5分）セッションに残り、その間にセッションを盗まれると、承認した内容のまま実行されうる。期限を短くすると、この放置された承認が残る時間を縮められる
- パスキーの追加では、承認の後に認証器での作成（保存先の選択、生体認証、クロスデバイスなら QR の読み取り）が挟まる。D48 で options に「残り1分以上」を求めているので、短くしすぎると追加ができない

本番では、操作ごとに期限を分ける（送金は1分、追加は5分など）のがよいと考える（推測。実際の利用者の操作時間は測っていない）。

### Q4 端末固定鍵（BE=0）を高リスク操作で必須にするか

一般向けには必須にしない（D52）。

- 実機で使った鍵はすべて同期型（BE=1）だった。BE=0 を必須にすると、多くの利用者の手元の鍵が使えなくなる（推測。同期型が主流であることは実機の2製品からの観察）
- `attestation: "none"` では、BE は認証器の自己申告にすぎない。R3・L4 は「BS=1 なら BE=1」「登録時と同じ BE」という整合性は見るが、BE=0 という申告が本当かは確かめられない。BE=0 を条件にするなら、attestation の検証（認証器の機種の証明）が前提になる
- 管理画面や高額の操作など、利用者を限定できる場面では、attestation を検証したうえで端末固定の鍵（セキュリティキー）を必須にする価値がある。これは別 PoC の候補（docs/02 §3 の1行目）につながる

### Q5 次に試す方式

M8 では決めない（D53）。5章に提案だけ残す。

## 5. 次の方向（提案）

### 5.1 パスキーを組み込んでできること

M6・M7 で作った「操作ごとの承認」は、送金以外にも使える。

| 案 | 内容 | このPoCとのつながり |
|---|---|---|
| 高リスク操作の承認の汎用化 | 送金先の登録、権限の変更、データの一括エクスポートなどを `StepupOperation` に足す。操作ごとに期限を分ける | `operationHash` と `OPERATION_GATE_CHECKS` をそのまま使える |
| 鍵の追加・削除の通知 | 鍵の追加・削除を、別経路（メールなど）で本人に知らせる。攻撃者が鍵を足しても本人が気づける | 3章の「攻撃者が追加した鍵」の残リスクを減らす |
| 取引内容をブラウザに表示させる承認 | Secure Payment Confirmation で、金額と支払先をブラウザの画面に出してから署名させる | 3章の画面改ざんへの対策。ステップアップの弱点を埋める |
| IdP にパスキーを置く構成 | Keycloak などの IdP でパスキー認証を行い、アプリは OIDC で受け取る。ステップアップは OIDC の認証強度の要求（`acr_values`、`max_age`）で表す | 自前の検証を IdP に任せたとき、何がアプリ側に残るかを比べられる |
| 管理画面の端末固定鍵 | attestation を検証し、許可した機種のセキュリティキーだけを受け付ける | 4章 Q4 の結論。D23 で `none` 以外を拒否している部分を広げる |
| セッションを端末に縛る | DBSC などで、ログイン後の Cookie を端末の鍵に縛る | パスキーがログインを、こちらがセッションを守る。3章の最大の残リスク |

### 5.2 この実装をライブラリにするなら

#### 今あるもの

- 6章の全項目を1項目1ファイルで持つ検証パイプライン。凍結した定数で、本番経路から外す手段がない
- 項目ごとの攻撃再現テスト（「外すと通る」）と、`@simplewebauthn/server` との差分テスト
- 改ざんした応答を作れるソフトウェア認証器

#### 汎用ライブラリとして足りないもの

| 観点 | 今の状態 | 必要なこと |
|---|---|---|
| attestation | `none` 以外を拒否（D23） | packed、tpm、android-key、apple などの形式の検証。FIDO の Metadata Service による機種の確認 |
| アルゴリズム・拡張 | ES256・RS256 のみ（`cose.ts` は Ed25519 の鍵を読めるが、`pubKeyCredParams` で要求せず R1 が拒否する）。拡張機能（credProps、prf など）は扱わない | 対応範囲を決めて広げる |
| 依存 | Express と `node:sqlite` のスキーマに直結 | 保存先とフレームワークを差し替えられる API（challenge・credential・セッションの保存をインターフェースにする） |
| 仕様への追従 | WebAuthn L3 の時点の実装 | 仕様の改訂、ブラウザ・認証器ごとの癖（K11 のような）への継続的な対応 |
| 保証 | 自分で書いたテストとレビューのみ | 外部のセキュリティレビュー、CBOR パーサーなどへの fuzzing、脆弱性報告の受付と修正の体制 |

#### 見立て

汎用の検証ライブラリとして公開する価値は低いと考える（推測）。成熟したライブラリがすでにあり、M5 の差分テストでこの実装と判定が一致した。足りないものを埋めて同じ水準に届いても、利用者にとっての違いが小さい。一方で、脆弱性への責任は同じだけ負う。

価値がありそうなのは、次の2つ。

1. **RP 向けの攻撃テスト集**: M5 で分かったとおり、ライブラリは challenge の結び付けや鍵の持ち主の確認をアプリに任せている。ソフトウェア認証器と攻撃シナリオ（C5・L2・S1 など）を切り出し、既存ライブラリで作ったサーバーに対して「アプリ側の確認が抜けていないか」を試すテストツールにする。検証ライブラリではなくテストの道具なので、責任の範囲も狭い
2. **ライブラリの上に載せる承認の層**: `StepupOperation`、操作ハッシュ、ゲート（S3 → S2）、追加 options の事前確認（D48）を、既存の検証ライブラリと組み合わせて使える形にする。M7 で踏んだ落とし穴（承認の単一スロット、作成と保存のずれ）をまとめて扱える

どちらも、進めるなら最初に「何を保証し、何を保証しないか」を README に書き、保存先の抽象化から始める。

## 6. 開発の進め方で学んだこと

- **攻撃再現テストを先に書くと、設計の誤りが早く見つかる**: C5 を Cookie で引いていた（M2）、L2 のセッション発行先（M3）は、どちらも「この項目を外すと通る」を書こうとして見つかった
- **レビューは毎回、本物の穴を見つけた**: PR ごとの自動レビューと最終レビューで、M2 の C4 より前に走るデコード（D24）と CBOR の再帰の深さ、M3 の中断した ceremony の Set-Cookie が後から届く問題、M6 のセッションへの縛り、M7 の承認のずれなどが見つかった。どれもテストは通っていた。逆に、M7 の見送った指摘のように「サーバーでは防げない」ものもあり、指摘をそのまま直すのではなく、何を壊すかを比べて決める必要があった
- **AI が動作確認できる範囲を広げる**: Chromium の仮想認証器で、登録からステップアップ、パスキーの追加・削除まで、人手なしで E2E を回せた。実機（1Password の挙動、画面の取り違え、Safari）は人が確かめる必要があり、M7 では実機でしか分からない発見が一番多かった
- **守らせたいルールは、破ったら検査が落ちる形にする**: 検証項目の一覧一致テスト、テストの skip 禁止の lint、マスキング検査。文章で書くだけのルールより確実だった
- **断定しない**: 仕様・公式資料・実機・テストで裏付けていない記述には（推測）と付けた（D32）。ベンダーの内部構成は外から確かめられないので、「そう説明されている」までしか書けない
