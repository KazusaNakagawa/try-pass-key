## M6 ステップアップ

- 設計（`docs/superpowers/specs/2026-11-24-m6-stepup-design.md`）と計画を作り、Native 実行（タスクごとのレビューなし、最後に1回）で実装した
- ステップアップ固有の検証を 6章に S1〜S3 として立てた（D36）。S1 は再認証の `STEPUP_CHECKS`、S2・S3 は送金直前の `TRANSFER_GATE_CHECKS`。どれも「外すと攻撃が通る」テストがある
  - S1 を外すと、盗んだセッションで攻撃者が自分のパスキーで承認でき、被害者として送金できる
  - S3 を外すと、5分を過ぎた承認と、1回の承認での2回目の送金が通る。承認なしの送金は S3 を外しても S2 が止める
- C5 のステップアップ側（行の `user_id` とセッションのユーザーの一致）を実装した。docs/01 には書いてあったが未実装だった
- 再認証が通ったらセッションIDを再発行する。`auth_at` と絶対期限は引き継ぐ
- 画面に送金のセクションを足した。`step_up_required` を受けたら自動でステップアップし、送り直す。E2E にも追加した
- 登録時の初期残高 100,000（D39）。既存の開発DBのユーザーは 0 のまま

## 気づき（M6）

- SQLite の `UPDATE ... RETURNING` は更新後の値を返す。承認を NULL にする UPDATE の RETURNING では消した NULL しか取れず、計画どおりに書いたら S2 が常に失敗した。テストが赤くなって判明し、「読んでから、読んだ値と一致するときだけ消す」形に直した（D38）
- ステップアップでは、ユーザーが ceremony の前に分かっているので、確かめる相手が `userHandle` ではなくセッションになる（WebAuthn L3 §7.2 手順6）。ログインの L2 をそのまま使うと、`userHandle` を返さない認証器で正当な承認が落ちうる
