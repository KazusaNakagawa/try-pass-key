## PR #11 レビュー指摘の対応

- 指摘10件（自動レビュー、コードを読んだだけで実行では確かめていないもの）
- 直したもの
  - 追加の verify がゲート（S3/S2）で拒否されたとき、「直近の ceremony」は登録の検証項目がすべて ✓ のまま、失敗欄にだけ S3 が出ていた。追加では検証欄にゲートの行も並べ、ゲートの結果を記録するようにした。テストを先に書き、落ちることを確かめてから直した
  - 追加・削除の後に `/api/me`・送金履歴・パスキー一覧をすべて取り直し、Signal API も2回呼んでいた。変わったものだけ取り直す
  - 保存した鍵を一覧から探し直していた。保存の関数が一覧の1行をそのまま返す
  - 鍵の一覧を `allowCredentials` / `excludeCredentials` に変換するクエリが3か所にあり、並び順もずれていた。`credentialDescriptors` にまとめた
  - AAGUID の表示名のコメントに、出典の GitHub アカウント名とリポジトリ名を書いていた。マスキングの規則に合わせて一般的な書き方にした
  - `toBase64Url` に揃えた
- 見送ったもの
  - [High] 1つの承認で2つのタブが同時に追加すると、後の verify が S3 で拒否され、認証器に鍵が残る
  - [High] 作成中に別のタブでステップアップすると、セッション ID が変わって C5 で拒否され、認証器に鍵が残る
  - [Medium] ブラウザが `timeout` を丸めると、作成が承認より長引きうる（推測）
  - いずれも作成と保存が原子的でないことから来る。サーバー側で塞ぐ案（options での予約、未使用の challenge があるあいだの拒否、ステップアップでセッション ID を変えない）は、どれも別のもの（やり直し、セッション固定対策）を壊す。限界として K12・D50 に記録した
  - [Medium] 鍵を削除してもセッションは失効しない: D47 で決めた残リスク（docs/01 §9）

## 気づき

- 「認証器にだけ鍵が残る」は、承認の扱いをどう工夫しても、通信の失敗ひとつで起きる。防ぐより、起きたときに消せる（Signal API、一覧からの削除）ことのほうが本筋だった。その Signal API が 1Password に効かないので、利用者が手で消すしかない
