### challenge の照合方法を一時 Cookie にした裏付け

候補は2つだった。

- (a) clientDataJSON に入っている challenge の値で `challenges` テーブルを検索する
- (b) options で作った行の ID を一時 Cookie で返し、verify ではその ID で行を引く

| 観点 | (a) 値で検索 | (b) 一時 Cookie |
|---|---|---|
| 署名済み応答が送信前に漏れた場合 | challenge の有効期限内なら、どのブラウザから送っても通る | Cookie を持つ元のブラウザからしか通らない |
| 実運用との対応 | 少数派 | 主流。多くのフレームワークは challenge をセッションに置き、Cookie で引く |
| 学習 | 「challenge が一致したか」だけを見る | 「誰に発行した challenge か」まで見る。別ブラウザに発行された challenge を流用する攻撃をテストで再現できる |
| 実装コスト | 小さい | Cookie を1つ足す程度 |

決め手は1行目。応答が漏れる経路（XSS での窃取、ログへの混入）は現実にありうる。(a) では challenge の有効期限の5分間、漏れた応答をそのまま攻撃者のブラウザから使える。(b) なら Cookie も同時に盗まれない限り通らない。Cookie は `HttpOnly` なので、XSS で応答を盗まれても Cookie は JavaScript から読めない。

ただし (b) が防ぐのは「別のブラウザへ持ち出して使う」経路だけである。XSS のスクリプトが被害者のブラウザの中から verify を送れば、Cookie は自動で付くので通ってしまう。XSS そのものへの対策（CSP など）は別に必要になる。

(b) の代償は、一時 Cookie を1つしか持てないことによる複数タブの上書き（K8）。PoC では失敗させて options を取り直せば足りると判断した。

この縛りは検証項目 C5 として独立させた。パイプラインから C5 だけを外すと別ブラウザからの応答が通ることを、攻撃再現テストで示す。

### 気づき

- challenge の検証には「値が一致するか」（C2）と「誰に発行したか」（C5）の2つの軸がある。前者だけでもリプレイは防げるが、漏れた応答の横取りは防げない
- `@simplewebauthn/server` は全項目を一括で検証するため、1項目だけ外して「通ってしまう攻撃」を見せることができない。学習目的を果たすには、検証を自分で持つ必要がある
- 検証を無効にするフラグを本番コードに作ると、それ自体が穴になる。テストでは検証のリストから1項目を除いて渡す形にし、本番経路には無効化の手段を残さない
- AI に守らせたいルールは、文章で書くだけでは破られうる。破ったら `yarn check` が落ちる形（検証 ID の一覧一致テスト、skip 禁止の lint）にすると機械的に止められる

## 追記: CI の追加

### やったこと

- `.github/workflows/ci.yml` を追加した（D15）。PR と `main` への push で動く
  - `mask-check`: `scripts/mask-check.sh` でホームディレクトリのパスとメールアドレスを検出する。個人名などは secret `MASK_PATTERNS` から渡す
  - `check`: `compose.yaml` があれば `docker compose run --rm server yarn check` を実行する。M1 前はスキップしてその旨を表示する
- actionlint と shellcheck をコンテナで実行し、指摘がないことを確認した

### 気づき

- 公開リポジトリでは「何を検出したいか」というパターン自体が個人情報になる。パターンは secret に置き、CI のログにはマッチした文字列を出さず「ファイル:行」だけを出す必要がある

- 個人名などの検出パターンを secret `MASK_PATTERNS` に登録した。PR の CI を再実行し、ログに `MASK_PATTERNS is not set` が出ず `mask-check: OK` になることを確認した

### マスキング検査をこの形にした意味

CLAUDE.md のマスキング規約は、これまで「コミット前に人が grep する」だけで守っていた。公開リポジトリでは一度 push すると取り消せない（キャッシュ・フォーク・検索インデックスに残る）ため、人の注意に頼らず CI で機械的に止める。

検出パターンは2層に分けた。

| 層 | 中身 | 置き場所 | 理由 |
|---|---|---|---|
| 汎用 | ホームディレクトリのパス、メールアドレス | `scripts/mask-check.sh` に直書き | 公開しても問題ない |
| 固有 | 本名、アカウント名、組織名など | ローカルの `~/.config/try-pass-key/mask-patterns`（リポジトリ外）と、その内容を登録した secret `MASK_PATTERNS` | パターン自体が個人情報になるため、リポジトリに書けない |

secret に置くことの評価は次のとおり。

- 登録後は管理者本人も値を読み出せず、他人の fork からの PR には渡されない。ログでは GitHub が値を `***` に置き換え、スクリプトもマッチした文字列を出さず「ファイル:行」だけを出す
- GitHub 社には暗号化された状態で渡る。アカウント名はリポジトリの URL で元々公開されているので、新たな露出はほぼない
- `gh secret set` には値をコマンド引数で渡さず、ファイルからリダイレクトした。会話やシェル履歴に値が残らないようにするため

運用:

- パターンを変えたら、ローカルのファイルを編集し `gh secret set MASK_PATTERNS < ~/.config/try-pass-key/mask-patterns` で登録し直す
- コミット前のローカル検査: `MASK_PATTERNS="$(cat ~/.config/try-pass-key/mask-patterns)" bash scripts/mask-check.sh`
- パターンファイルの中身は `cat` で表示して会話やログに貼らない

### 気づき（追加）

- `gh auth refresh -s workflow` でスコープを足しても、git が macOS キーチェーンの古いトークンを使っていると、ワークフローファイルの push は拒否されたままになる。今回は `git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push` でそのコマンドだけ gh のトークンを使って回避した

### 課題

- git の認証情報を恒久的に直す（`gh auth setup-git` か、キーチェーンのトークン更新）。直すまではワークフローファイルの push に上記の回避策が要る

  - `attacks.test.ts`: 11項目すべてで「全検査では拒否される」「その検査だけ外すと通る」の両方を示す

### 気づき

- C5 を独立した検査にするには、challenge の行を Cookie で引いてはいけない。Cookie で引くと縛りが「行の取り出し方」に埋め込まれ、外して攻撃を再現することができない。値で引いて C5 で比べる形に変えた（D21）。設計の段階では見えず、攻撃再現テストを書こうとして初めて気づいた
- 攻撃によっては、狙った検査より前の検査で落ちる。challenge の二重使用は、C4 があると行が消えているので C2（未発行）で拒否される。C4 を外すと行が残るので通る。「どの検査が拒否したか」と「どの検査を外すと通るか」は一致しないことがあるので、攻撃シナリオに `rejectedBy` を別に持たせた
- R2（credentialId の重複）を外しても、DB の主キーが最後の砦として二重登録を止める。検証とスキーマ制約の二重化は、レビューで入れた CHECK 制約と同じ考え方
- cbor-x は整数キーの Map を、独自のタグ 259 を付けてエンコードする。実際の認証器はこのタグを出さないので、ソフトウェア認証器では無効にした。この設定項目は cbor-x の型定義にないため、型を広げて渡している
- authenticatorData の公開鍵（CBOR）には長さの前置きがなく、拡張データ（CBOR）が直後に続く。公開鍵のバイト列を切り出すには、CBOR の1項目の長さを測る必要がある

| 公開鍵 | 77 バイト、先頭 `A5 01 02 03 26 20 01` | 5項目の CBOR マップ。`kty=2`（EC2）、`alg=-7`（ES256）、`crv=1`（P-256） |
| signCount | 0 | 同期型パスキーはカウンタを使わない。A4 の「両方 0 なら許容」のケース |
| BE / BS | 1 / 1 | 同期可能で、同期済み |
| AAGUID | `bada5566-a7aa-401f-bd96-45619a55120d` | 1Password の AAGUID |
| transports | `hybrid`, `internal` | |

- `attestation: "none"` なら AAGUID はゼロになると思っていたが、1Password は自社の AAGUID を返した。1Password は拡張機能としてページ内で WebAuthn を処理するため、ブラウザが attestation を `none` に置き換えて AAGUID をゼロにする処理を通らないと考えられる。AAGUID を記録しておくと、どの保管庫の鍵かがわかる（02 の2章の「保管庫が開かれれば使われる」リスクの判断材料になる）。設計書とコメントの「none の場合はゼロ」を直した

- 2回登録したので、1Password に `localhost` のパスキーが2つできた。アイテムの「Web サイト」欄は `https://localhost` と `http://localhost:5174` で違ったが、これは 1Password の表示用の情報で、鍵はどちらも RP ID `localhost` に紐づく。認証器は RP ID（ドメイン）単位で鍵を選び、ポートやスキームは区別しない。一方サーバーの C3 は origin（スキーム + ホスト + ポート）を完全一致で比べる。鍵の選択はドメイン単位、検証は origin 単位という2段構えになっている
- 2つとも表示名は `test-user-1` で、1Password の一覧では見分けがつかない。サーバー側では userHandle（乱数）が別なので別ユーザー。表示名は人間向けのラベルにすぎず、識別には使われない
- 1Password の画面キャプチャには、右上にアカウント名とアバターが写る。記事に使うときは隠す

## 追記: M3（ログイン）の実装

### やったこと

- 検証 A4（signCount）、L1（credential が登録済み）、L2（credential が userHandle のユーザーのもの）、L3（署名検証）を追加し、`AUTHENTICATION_CHECKS` を作った。L3 は `node:crypto` の `verify` で `authenticatorData ‖ SHA-256(clientDataJSON)` を検証する（ES256 は DER 形式の署名）
- API: `POST /api/login/options`（allowCredentials は空）、`POST /api/login/verify`、`GET /api/me`、`POST /api/logout`
- セッション: トークンは Cookie にだけ置き DB には SHA-256 を保存（D27）。ログイン・登録完了時に ID を再発行し、既存のセッションを破棄する。アイドル 30 分、絶対 8 時間。期限切れは起動時と1分ごとに削除する。登録完了時にもセッションを発行するようにした（D22 の先送り分）
- ログインのセッションは userHandle が指すユーザーに発行する（D28）
- Web: ログインボタン、Conditional UI（`autocomplete="username webauthn"` と `useBrowserAutofill`）、ログイン状態の表示、ログアウト
- E2E（D20 で M3 に回した分）: Playwright 公式イメージと Chromium の仮想認証器で、登録 → ログアウト → ログインを人手なしで通す。CI にも入れた（D29）
- DB スキーマにバージョンを付け、古い DB は起動時に拒否する（D26）
- テストは 120 件から 180 件 + E2E 2件になった。ログインの攻撃再現は12項目すべてにある

### 気づき

- ボリュームの DB が M1 時点のスキーマのままだった。`CREATE TABLE IF NOT EXISTS` は既存テーブルを黙って残すので、PR #3 のレビューで足した主キーの NOT NULL、challenge の UNIQUE、用途ごとの CHECK 制約は、手元の DB には一度も効いていなかった。テストは毎回新しい DB で動くので気づけない。スキーマのバージョンで古い DB を拒否するようにした
- L1 は外しても攻撃が通らない。L2 と L3 は保存済みの credential がないと判定できず、L2 が拒否する。R2 と主キーの関係と同じく、L1 は後続の検証の前提になっている。攻撃シナリオに「外しても別の検証が拒否する」という期待値を持たせた
- L2 の意味は、セッションを誰に発行するかで変わる。credential の持ち主に発行すると、L2 を外しても無害で、検証の意味が見えない。仕様どおり userHandle のユーザーに発行すると、L2 を外したときに「自分の鍵 + 被害者の userHandle」で乗っ取りが成立する。テストでこれを示した
- Chromium の仮想認証器は、Conditional UI の要求にも即座に応答する（K10）。ログアウト直後に再ログインしてしまうので、E2E を Conditional UI 用とボタン用に分けた
- E2E が実際のバグを見つけた。Conditional UI は options を取ってから待ち状態に入るので、取得中に中断しても、取得後に待ち状態が始まってしまう。ボタンでのログインを後から中断することもありうる。中断を世代番号で管理して直した
- 仮想認証器で登録した鍵は signCount が 1 から始まり、ログインのたびに増える（端末固定の鍵の挙動）。1Password の同期パスキーは 0 のまま。A4 の両方の分岐を実際に通せた

### 実機での確認（Chrome + 1Password）

ユーザーが `docker compose down -v` で DB を作り直し、1Password の古いパスキーを削除してから試した。

- 登録 → ログアウト → パスキーでログインが成功した。credentials の `last_used_at` が更新され、`sign_count` は 0 のまま（同期パスキー。A4 の「両方 0 なら許容」の分岐を実機で通った）。sessions はログイン時刻の1件だけで、登録時のセッションはログアウトで消えている
- 最初、パスキーを作る前に「パスキーでログイン」を押したところ、1Password ではなく Chrome 自身のダイアログが出て、スマホ用の QR コードとセキュリティキーを案内された。このブラウザのどこにも `localhost` のパスキーがないとき、Chrome は「別のデバイスのパスキー」（ハイブリッド）を代わりに出す。1Password はパスキーを持っていない RP には応答しない。利用者からは「QR コードを用意しないといけない」ように見えて紛らわしい。実サービスでは、パスキーが見つからなかったときの案内（登録への導線）が要る

- Conditional UI も実機で動いた。ユーザー名の入力欄をクリックすると、欄の下に Chrome のオートフィル候補として `localhost` のパスキーが出た。選ぶと Chrome のパスキー選択と macOS の「サインイン」シート（パスキーの提供元: 1Password）が出て、ログインできた。処理は「ページの待ち受け要求 → Chrome のオートフィル → macOS → 1Password」と渡っている。ボタンでのログインは、1Password が画面上部に出すポップアップから選ぶ形だった
- 1Password の項目名は、WebAuthn で渡した `user.name`（`test-user-1`）ではなく、ページのユーザー名欄に入っていた文字（`user-dev-1`）になっていた。M2 の時点ではユーザー名欄がなかったので `test-user-1` で保存されていた。パスワードマネージャーの表示名は、サーバーの識別（userHandle）とは無関係なラベルにすぎない
- 画面の不具合: ログインに成功すると「パスキーでログイン」の欄ごと非表示になり、その中の結果表示（「ログインしました（オートフィル）」）が見えなかった。E2E は非表示の要素の文字も読めるので気づけなかった。結果表示を「ログイン状態」の欄に移し、E2E に `toBeVisible` を足した

- 失敗: E2E を開発用のスタックに対して `WEB_PORT` を付けずに実行した。compose が設定の差（5174 → 5173）を見て web と server を作り直し、ユーザーがブラウザで開いていた 5174 番が切れた。さらに E2E のテストユーザー2人が開発用の DB に登録された。スタックを 5174 番で起動し直し、E2E が作った行を消した。`sqlite3` の接続では外部キーが無効なので、ユーザーを消しても `ON DELETE CASCADE` が働かず、credential とセッションが孤立して残った。これも手で消した
- 再発防止: `scripts/e2e.sh` で、専用のプロジェクト名・ボリューム・ポートの使い捨てスタックを立てて E2E を走らせ、終わったら消すようにした。CLAUDE.md に「開発用スタックに E2E を当てない」「DB で削除する前に `PRAGMA foreign_keys = ON`」を書いた

- DB クライアントで中身を見たいという要望があったが、DB は名前付きボリュームの中（Rancher Desktop の VM 内）にあり、ホストの Finder からは開けない。`scripts/db-snapshot.sh` を足した。SQLite の `.backup` で整合した写しを作り、`docker compose cp` でホストに取り出す（既定は `~/Downloads`、リポジトリ内には書かせない）。WAL モードなので `app.db` だけをコピーすると直近の書き込みが抜ける。ホストに直接マウントしてライブで見る方法は、ファイル共有の遅延（K6）で SQLite のロックが壊れうるので採らなかった

- DBeaver でスナップショットを開き、セッションの設計を実データで確かめた。`expires_at` は `auth_at` のちょうど8時間後、`last_seen_at` はアクセスのたびに進む。ブラウザの `session` Cookie の値を SHA-256 → base64url にすると、DB の `sessions.id` と一致した。DevTools の Console で `document.cookie` を見ても `session` は出てこない（HttpOnly）
- DB の BLOB 列（credentialId、公開鍵、userHandle）が文字化けして見えるのを「暗号化されている」と受け取られた。実際はバイナリをそのまま保存しているだけで、公開鍵は秘密ではないので暗号化の必要がない。ハッシュ（sessions.id）、暗号化（この PoC では未使用）、バイナリの違いは、記事で説明しておく価値がある
- ここまでの確かめ方（実機での登録・ログイン、DB スナップショットと DBeaver、COSE 鍵の読み方、Cookie とハッシュの照合、HttpOnly）を `docs/03-hands-on-verification.md` にまとめた
