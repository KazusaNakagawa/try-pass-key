# M6 ステップアップ Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 送金の直前にパスキーでの再認証を要求し、承認を送金内容に紐づけて使い捨てにする。ステップアップ固有の検証 S1〜S3 を 6章に足し、外すと攻撃が通ることをテストで示す。

**Architecture:** 再認証は既存のログインのパイプラインを流用した `STEPUP_CHECKS`（L2 の代わりに S1）で検証し、成功したらセッションIDを作り直して承認（`stepup_at`、`approved_tx_hash`）を記録する。送金の前に `TRANSFER_GATE_CHECKS`（S3 → S2）で承認を消費してから内容を照合し、通ったら残高の減算と履歴の追加を1つのトランザクションで行う。

**Tech Stack:** TypeScript、Express、node:sqlite、zod（`@app/shared`）、vitest、Playwright（仮想認証器）、`@simplewebauthn/browser`

**Spec:** `docs/superpowers/specs/2026-11-24-m6-stepup-design.md`

## Global Constraints

- コマンドはすべて `docker compose` 経由。各タスクの完了条件は `docker compose run --rm server yarn check` が通ること
- 既存の検証項目（C1〜L4）、既存の攻撃テスト、ログインの L2 を消さない・弱めない。検証を飛ばすフラグや引数を本番コードに入れない
- route は検証項目のリストを渡さない。`runInspected({ ceremony })` が凍結した定数を選ぶ
- `STEPUP_TTL_MS = 5 * 60 * 1000`、`INITIAL_BALANCE = 100000`、`amount` は 1 以上 1,000,000 以下の整数、`to` は前後の空白を除いて 1〜64 文字
- 取引ハッシュは `base64url(SHA-256(JSON.stringify({ kind: 'transfer', to, amount })))`（キーはこの順で組み立てる）
- エラーコード: S1 → `credential_not_owned`（400）、S2・S3 → `step_up_required`（401）。残高不足 → `insufficient_funds`（400）
- `SCHEMA_VERSION` は変えない
- コミットは英語、ドキュメントは日本語。マスキング（CLAUDE.md）を守る。テストの表示名は `test-user-1` 形式
- Rancher Desktop のファイル共有の遅れで、書き込み直後の `yarn check` が構文エラーになることがある。再実行で確かめる

## Review Focus

1. 同じ承認で同時に2つの送金が来る → 片方だけが通る（消費の UPDATE が1文で、`RETURNING` の有無で判定）。Task 4 のテストで固定する
2. 形式違反の送金リクエスト（`amount: 0`、文字列、`to` が空白だけ）→ 400 `invalid_request` で、承認は消費されない。Task 5 のテストで固定する
3. ステップアップの応答に `userHandle` が無い（`allowCredentials` 指定時に返さない認証器）→ 承認できる。Task 2（S1）と Task 3 のテストで固定する
4. 承認後に別のブラウザ（別のセッション）から送金 → 承認はセッションに付くので 401。Task 5 のテストで固定する
5. ステップアップ後に古いセッションの Cookie を使う → 401 `unauthenticated`（再発行で古い行は消える）。Task 5 のテストで固定する
