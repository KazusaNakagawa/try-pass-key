# M5 差分テスト 設計（短い版）

- 作成日: 2026-11-24
- 対象: docs/01 §11 の M5「6章の全項目に対し、正常系と『その項目を外したパイプラインでは攻撃が通る』異常系のテストがある。差分テストで `@simplewebauthn/server` と判定が一致する」

## 現状

- 異常系: `server/test/attacks.test.ts`（登録13項目）と `server/test/login-attacks.test.ts`（ログイン13項目）に、全項目分のシナリオがある。「全項目にシナリオがある」こと自体もテストしている
- 正常系: `server/src/webauthn/checks/*.test.ts`（18項目）にある
- 残りは差分テスト。`@simplewebauthn/server` は未導入

## 目的

自前の検証パイプラインが、広く使われているライブラリと同じ応答を受理・拒否することを示す。判定が食い違う項目は、なぜ食い違うのかを一覧にする。その一覧自体が「ライブラリが何を見て、何をアプリに任せているか」の学習結果になる。

## ゴール / 非ゴール / やってはいけないこと

- ゴール: 正常系と、6章の各項目の攻撃シナリオの応答を、自前のパイプラインと `@simplewebauthn/server` の両方に通し、受理・拒否を比べる。食い違いは理由付きの期待値としてテストに固定する
- 非ゴール: ランダムな変異による比較（案B）、attestation `none` 以外の形式、拒否理由の文言の一致
- やってはいけないこと: 検証項目や既存の攻撃テストを変えること。ライブラリを本番コードから使うこと（`server/src/webauthn/CLAUDE.md`、D11）

## 作り方の比較

| 案 | 内容 | 採否 |
|---|---|---|
| A. 既存の攻撃シナリオで比べる | 正常系と各項目の攻撃シナリオの応答を両方に通し、食い違いを理由付きで固定する | **採用**（ユーザーが選択）。何を比べたかが読め、食い違いの一つ一つに理由を書ける |
| B. ランダムな変異で比べる | フラグやバイトをランダムに書き換えて大量に比べる | 不採用。依存が増え、拒否理由の違いという雑音の整理が重い |
| C. A に限られた総当たりを足す | A に加えてフラグの全組み合わせなど | 不採用。M5 の完了条件には A で足りる |

## 設計

### 依存

`@simplewebauthn/server@14.1.0`（2026-11-06 公開。Node 22 以上）を `@app/server` の devDependency に完全一致のバージョンで入れる。

### テスト（`server/test/differential.test.ts`）

ケースの表を1つ持つ。各ケースは次を持つ。

- `check`: 対応する6章の項目（正常系は `null`）
- 応答の作り方: 既存の harness（`RegistrationHarness` / `LoginHarness`）と `SoftAuthenticator` で、攻撃シナリオと同じ改ざんをした応答 JSON を作る
- 自前の判定: 応答から context を作り、`REGISTRATION_CHECKS` / `AUTHENTICATION_CHECKS` をすべて通す。受理、または拒否した項目 ID
- ライブラリの判定: `verifyRegistrationResponse` / `verifyAuthenticationResponse` を呼び、`verified: true` なら受理、`false` か例外なら拒否
- 期待値: 自前の判定と、ライブラリの判定（`accept` / `reject`）。食い違うケースには理由の分類と1行の説明を付ける

ライブラリに渡す値は、普通のアプリが渡すものにする。

- `expectedChallenge`: そのブラウザに発行した challenge（options の値）
- `expectedOrigin` / `expectedRPID`: `RP_ORIGIN` / `RP_ID`
- `requireUserVerification: true`、`supportedAlgorithmIDs`: options で要求したもの
- ログインの `credential`: 応答の credential ID で DB から引いた保存済みの鍵（id、publicKey、counter）

### 食い違いの分類

| 分類 | 意味 | 該当しそうな項目（ライブラリのソースを読んだ時点の見込み。テストで確定する） |
|---|---|---|
| 一致 | 両方が受理、または両方が拒否 | C1、C3（origin）、A1、A2、A3、A4、R1、R3、L3 |
| アプリの責務 | ライブラリは、アプリが渡した値と比べるだけ。値を正しく用意するのはアプリの仕事 | C2（期限切れ）、C4（使い捨て）、C5（ブラウザとの結び付け）、R2（未登録か）、L1（登録済みか）、L2（持ち主の一致） |
| ライブラリが見ない | 応答だけで判定できるが、ライブラリは判定しない | C3 の `crossOrigin: true`（`topOrigin` がないとき）、R4（ID の長さ）、R5（弱い RSA 鍵）、L4（BE の変化） |

「アプリの責務」のうち、アプリがライブラリを呼ぶ前に判断するもの（L1 で鍵が見つからないなど）は、ライブラリを呼ばず「比較対象外」として理由だけを固定する。

### 網羅の確認

`REGISTRATION_CHECKS` と `AUTHENTICATION_CHECKS` の全項目 ID が、表のいずれかのケースに現れることをテストする（既存の攻撃テストと同じ考え方）。
