# 背景: なぜパスキーを実装して理解するのか

- 作成日: 2026-11-23
- 位置づけ: PoC（[01-architecture-proposal-poc.md](./01-architecture-proposal-poc.md)）の前提となる問題意識をまとめる

## 1. 問題意識

サイバー攻撃の報道が続いている。特に懸念しているのは、侵入そのものより、その後に起きる二次被害である。

攻撃者が正規ユーザーの認証情報やセッションを手に入れると、システムから見たその操作は「正規ユーザーによる正規の処理」になる。送金、出金、権限変更、データの一括エクスポートといった処理が正常系として通ってしまい、資産が抜かれる。不正アクセス検知やWAFは「怪しい通信」を見るので、正規の認証を通った操作はすり抜けやすい。

つまり、守りの要は「この操作を本当に本人がしているのか」をシステムが確かめられるかどうか、すなわち認証にある。

## 2. 正規ユーザーになりすまされる典型的な経路

| 経路 | 手口 | パスワード + SMS/TOTP で防げるか |
|---|---|---|
| フィッシング | 偽サイトにID・パスワード・OTPを入力させ、攻撃者が中継して本物にログインする（AiTM） | 防げない。OTPも中継される |
| クレデンシャルスタッフィング | 他サービスから漏れたID・パスワードの組を総当たりで試す | 多要素があれば多くは防げる |
| サーバー側の漏洩 | パスワードハッシュが流出し、オフラインで解析される | ハッシュ強度次第。漏れた時点で全ユーザーがリスクを負う |
| SIMスワップ・SMS傍受 | 電話番号を乗っ取りSMSのOTPを受け取る | 防げない |
| MFA疲労攻撃 | プッシュ通知を連打して誤って承認させる | 防げない |
| セッション窃取 | マルウェアやXSSでログイン後のCookieを盗む | 防げない（認証後の話なので） |

共通しているのは、「秘密（パスワードやOTP）を人間が入力し、それがネットワークを流れる」構造である。人間は本物と偽物のサイトを見分けられないので、秘密は偽サイトにも渡ってしまう。

## 3. パスキーが変えること

パスキー（FIDO2 / WebAuthn の discoverable credential）は、この構造を変える。

1. **秘密がサーバーに存在しない**。サーバーが持つのは公開鍵だけで、漏れても攻撃者はログインできない。
2. **秘密がネットワークを流れない**。端末内の秘密鍵でチャレンジに署名し、その署名だけを送る。
3. **ドメインに紐づく**。ブラウザが署名対象に「どのオリジンで要求されたか」を埋め込み、鍵自体もRP ID（ドメイン）に紐づく。偽サイト `examp1e.com` では本物 `example.com` の鍵が使われない。人間が見分けなくても、仕組みとしてフィッシングが成立しない。
4. **本人確認が端末内で完結する**。指紋・顔・PINは端末の外に出ず、サーバーは「端末が本人確認した」というフラグ（UV）だけを受け取る。

表2の経路のうち、フィッシング、スタッフィング、サーバー側漏洩、SIMスワップ、MFA疲労はパスキーで構造的に潰せる。

## 4. パスキーだけでは解決しないこと

ここを理解しておかないと、「パスキーを入れたから安全」という誤解につながる。

- **ログイン後のセッション窃取**。パスキーはログインの瞬間を守る。発行されたセッションCookieが盗まれれば、攻撃者は正規ユーザーとして振る舞える。
- **端末そのものの乗っ取り**。ロック解除された端末を操作されれば、パスキーも使われる。
- **アカウント復旧経路**。「パスキーを失くした人はメールで復旧」にすると、そこが最弱点になる。
- **同期パスキーのクラウドアカウント**。iCloudキーチェーンやGoogleパスワードマネージャーが乗っ取られると、同期されたパスキーも渡る。

二次被害（正規ユーザーとして資産を抜かれる）への対策としては、ログイン時だけでなく、**高リスク操作の直前にもう一度パスキーで本人確認する（ステップアップ認証）** ことが重要になる。PoCではこの点も実装対象に含める。

## 5. このPoCで得たい知見

- 登録（attestation）と認証（assertion）で、ブラウザ・認証器・サーバーの間で何がやり取りされているかを、自分の手で追えるようになる
- サーバー側で何を検証しなければならないか（challenge、origin、RP ID、フラグ、署名、カウンタ）と、検証を一つ省くと何が起きるかを理解する
- 同期パスキーと端末固定の鍵の違い、discoverable credential（ユーザー名なしログイン）の仕組みを理解する
- ステップアップ認証で「ログイン済みでも高リスク操作は本人確認する」設計を体験する
- パスキーで防げる脅威と防げない脅威の境界を、自分の言葉で説明できるようになる

本番サービスの構築は目的にしない。理解のために、ライブラリが隠している部分もログや可視化で見えるようにする。

## 6. 進め方の方針

- **Docker で構築し、試して壊せるようにする**。ホストの global 環境（Node.js、npm パッケージ、DB）には手を入れず、すべてコンテナ内で完結させる。壊したら `docker compose down -v` で消して作り直せばよい状態を保つ。
- **パスキーにこだわりすぎない**。パスキーはログインを守るには現時点で最有力だが、4章のとおりログイン後のセッション窃取や取引の誤承認は防げない。セッションを端末に縛る方式（DPoP、DBSC）や取引内容の別経路確認など、より適した方式や組み合わせるべき方式があれば、別PoCとして試す。候補は [02-knowledge-passkey.md](./02-knowledge-passkey.md) の3章に挙げた。
