# 調査ナレッジ: パスキーの実運用リスクと他の認証方式

- 作成日: 2026-11-23
- 位置づけ: 検討中に調べた知見の置き場。背景は [00-background.md](./00-background.md)、PoC の設計は [01-architecture-proposal-poc.md](./01-architecture-proposal-poc.md) を参照

## 1. 試験用に作ったパスキーは普段使いに影響するか

結論として、試す分には問題ない。

- パスキーは RP ID（ドメイン）に紐づく。`localhost` 用の鍵は `localhost` でしか呼ばれず、銀行や Google など他サイトで使われることはない。
- 既存のアカウントのパスキーが書き換わったり消えたりすることもない。
- 影響は、パスワード管理画面に「localhost」のパスキーが溜まって一覧が散らかる程度である。

気をつける点は2つある。

- **終わったら削除する**。macOS はシステム設定の「パスワード」、Chrome は `chrome://password-manager` から消せる。同期されていれば1か所で消すと全端末から消えるはずだが、確かめていない（推測）。
- **表示名に個人情報を入れない**。登録時の表示名（`user.name` / `user.displayName`）は認証器に渡される。WebAuthn 仕様では、認証器が必ず保存するのは userHandle（`user.id`）だけで、表示名を保存するかは認証器の任意である（WebAuthn L3 §6.3.2。確認画面での表示も SHOULD）。1Password は保存しており、一覧に `test-user-1` が出た（[worklog 2026-11-23](./worklog/2026-11-23.md)）。同期型なら他の端末にも渡ると考えられる（推測）。`test-user-1` のような名前にする。

### 1.1 消したパスキーを認証器に伝える（Signal API）

サーバーで鍵を消しても（DB の作り直し、M7 の削除）、認証器にはパスキーが残る（docs/01 K2）。WebAuthn L3 の Signal API は、RP から認証器にそれを伝える仕組みである。

- `PublicKeyCredential.signalUnknownCredential({ rpId, credentialId })`: その鍵はもう受け付けない
- `PublicKeyCredential.signalAllAcceptedCredentials({ rpId, userId, allAcceptedCredentialIds })`: このユーザーで受け付ける鍵はこれだけ（それ以外は消してよい）
- `PublicKeyCredential.signalCurrentUserDetails`: 表示名の変更を伝える（本PoCでは使わない）

いずれもユーザーの操作なしで呼べ、結果は返らない（Promise は認証器が何をしたかを教えない）。消すか隠すかは認証器が決める。本PoCは M7 で、一覧の取得・削除の後に `signalAllAcceptedCredentials`、L1 で拒否されたログインの後に `signalUnknownCredential` を呼ぶ（`web/src/signal.ts`）。1Password や iCloud キーチェーンでの実際の効き方はまだ確かめていない（docs/03 の手順で確かめる）。

## 2. 1Password などに保存したパスキーは盗まれるか

### 結論

保管庫が開かれれば、中のパスキーも使われる。

同期型のパスキーは、秘密鍵を端末の外（保管庫）に持ち出して端末間で同期する。そのため、保管庫を開ける者は秘密鍵を使え、本人として認証できる。ここまでは「同期する」という性質から言える。

保管庫の中で秘密鍵がどう暗号化され、どの鍵で復号されるかは各社の実装次第で、確認していない。iCloud キーチェーン、Google パスワードマネージャーも同じ構造だと考えているが、裏付けはない（推測）。

### 突破のされ方ごとのリスク

| 突破のされ方 | パスキーは使われるか | 理由 | 根拠 |
|---|---|---|---|
| 1Password のサーバー侵害 | ほぼ使われないと考えている | 1Password は保管庫をエンドツーエンド暗号化し、暗号鍵はアカウントパスワードと Secret Key を組み合わせて作り、1Password はどちらも受け取らない、と説明されている。サーバー側の実際の構成は確認できない | 1Password 公式説明（[1Password のセキュリティ](https://support.1password.com/1password-security/)、[Secret Key](https://support.1password.com/secret-key-security/)）。実際の構成は未確認 |
| マスターパスワードだけ漏洩 | 新しい端末からはほぼ使われないと考えている | 上と同じ説明に従えば、Secret Key も要る。ログイン済み端末を触られる場合は別 | 1Password 公式説明（同上）。実際の構成は未確認 |
| ロック解除中の端末にマルウェア | 使われると考えている | 保管庫が開いている間は鍵を使える状態にある（上の「同期する」性質から言える）。マルウェアが利用者の操作なしに使えるか、鍵を取り出せるかは実装次第 | 前半は同期の性質から導ける。後半は推測 |
| アカウント復旧の悪用 | 使われると考えている | 復旧手段（1Password なら Emergency Kit など）で保管庫を開けられるなら、その管理が弱点になる | 推測 |
| フィッシングサイトへの誘導 | 使われない | ブラウザ（クライアント）は、RP ID が呼び出し元 origin のドメインと一致するかその上位ドメインであることを確かめ、違えば拒否する。認証器は RP ID が一致する鍵だけを候補にする。サーバーは署名対象の origin を照合する。偽ドメインからは正規サイトの RP ID を指定できないので、鍵は呼ばれない | WebAuthn L3 §5.1.3・§5.1.4（ブラウザの照合）、§6.3.3（認証器の絞り込み）。サーバー側の origin 照合（C3）は本PoCのテストで確認 |

### パスワードとの比較

保管庫を突破されたときの被害は、パスワードを保管庫に入れていた場合と同程度だと考えている（推測）。一方、パスキーはフィッシングで使われず（WebAuthn 仕様）、サーバーには公開鍵しか置かないので、サーバーから漏れても秘密鍵は漏れない（WebAuthn 仕様。本PoCの DB にも公開鍵しかない）。この2点から、パスキーのほうが安全で、1Password に保存すること自体は悪い判断ではないと判断している。保管庫側のリスクを比べた結果ではない。

### 対策

| 立場 | 対策 |
|---|---|
| 利用者 | 重要なアカウントには端末固定の鍵（YubiKey 等のセキュリティキー、同期しない鍵）を使う。同期しない鍵は保管庫に入らないので、保管庫を突破されても使われない。秘密鍵がハードウェアから取り出せないことは、Yubico の開発者向けページでは「端末に安全に保存される」までしか確認できず、取り出せないとの明記は見つけていない（推測） |
| 利用者 | 1Password 自体を守る。強いマスターパスワード、Emergency Kit の厳重保管、自動ロック時間の短縮（効果の大きさは推測） |
| サービス提供者 | 送金など高リスク操作の直前に再認証を要求する（PoC 5.3 のステップアップ認証） |
| サービス提供者 | BE/BS フラグ（同期型か）や AAGUID（どの認証器か）を見て、高リスク操作では端末固定の鍵だけを受け付ける |

PoC では AAGUID と BE/BS を記録・表示する。実機では、1Password で登録した鍵が BE/BS = 1/1、AAGUID が 1Password の値だった（[worklog 2026-11-23](./worklog/2026-11-23.md)）。Touch ID は鍵を使うときの本人確認の手段で、鍵が同期するかは保存先で決まる。macOS の Chrome では保存先が Google パスワードマネージャー（同期・既定）、iCloud キーチェーン（同期）、Chrome プロファイル（同期しない）から選ばれる（[Google の対応環境一覧](https://developers.google.com/identity/passkeys/supported-environments)）。端末固定の鍵（Chrome プロファイル保存やセキュリティキー）とはまだ見比べていない。

## 2.5 検証ライブラリは何を見て、何をアプリに任せているか

M5 の差分テスト（docs/01 §6.6、`server/test/differential.test.ts`）で、`@simplewebauthn/server` 14.1.0 と自前の検証の判定を比べた結果。根拠はテストの実行結果と、ライブラリのソース（`verifyRegistrationResponse.js`・`verifyAuthenticationResponse.js`）。

- ライブラリは「渡された期待値と応答が合っているか」を見る。challenge が期限内か、使用済みでないか、どのブラウザに発行したものかは、アプリが `expectedChallenge` を用意する段階で決める。ライブラリに「その時点の正しい challenge」を渡し、使ったらすぐ消すのはアプリの仕事
- ログインでは、credential ID で鍵を探すこと、その鍵の持ち主と `userHandle` が同じユーザーかを確かめること、返ってきた BE/BS を登録時の値と比べること（WebAuthn L3 §7.2、docs/01 L4）もアプリの仕事。ライブラリは渡された鍵で署名を検証するだけなので、攻撃者が自分の鍵で署名して被害者の `userHandle` を送っても受理する（L2）
- 応答だけで判定できるのにライブラリが受理したものもある。1023 バイトを超える credential ID（WebAuthn L3 §7.1 で RP が拒否する手順として挙がっている、docs/01 R4）、1024 ビットで e = 3 の RSA 鍵（docs/01 R5）、`crossOrigin: true` の応答（このPoC は iframe からの呼び出しを許さない方針、docs/01 C3）
- ライブラリを使う場合も、これらはアプリ側で足す必要がある

## 3. パスキー以外の方式（別PoC候補）

パスキーはログインを守る有力な手段だと考えているが、唯一の正解とは限らない。PoC の脅威モデル（01 の9章）で残るリスクの多くは、ログイン後のセッションや取引承認に関するもので、パスキーとは別の仕組みが効く。

| 候補 | 何を解決するか | パスキーとの関係 | 試す価値（筆者の見立て） |
|---|---|---|---|
| ハードウェアセキュリティキー（端末固定の FIDO2 鍵）+ attestation 検証 | 同期元アカウント乗っ取りのリスク（2章）。認証器の機種を限定できる | パスキーと同じ WebAuthn。設定（attestation、BE=0 の要求）が違う | 高。本PoCの延長で試せる |
| DPoP / Device Bound Session Credentials（DBSC） | ログイン後のセッション窃取。トークンや Cookie を端末の鍵に縛り、盗んでも別端末では使えなくする | 補完関係。パスキーはログイン、こちらはセッションを守る | 高。二次被害対策に直結する |
| mTLS（クライアント証明書） | 端末そのものの認証。管理端末だけに操作を許す | 補完関係。社内システムや管理画面向け | 中。証明書の発行・失効運用も含めて学べる |
| OIDC / OAuth 2.0 で IdP に認証を委譲 | 認証を自前で持たないことによる実装ミスの削減。IdP 側でパスキーやリスクベース認証を使える | 置き換えではなく、パスキーを IdP 側に置く構成 | 中。Keycloak 等をコンテナで立てて試せる |
| 取引署名・別経路での取引確認 | 画面改ざんによる誤承認（Man-in-the-Browser）。取引内容を別端末に表示して承認させる | 補完関係。PoC 5.3 のステップアップの弱点を埋める | 中。資産を扱うなら本番では要検討 |
| リスクベース認証（端末・場所・振る舞いの変化を検知） | 正規の認証を通った不審な操作。いつもと違う操作だけ追加認証する | 補完関係。ステップアップの発動条件になる | 低〜中。データがないと効果を測りにくい |

SMS・TOTP のワンタイムパスワードは、利用者がどのサイトにも打ち込める文字列で origin に縛られないので、偽サイトに入力されたコードはそのまま正規サイトへ中継されうる。メールのマジックリンクも、リンクを開いた端末やログインを始めた端末に結びつけない実装では、偽サイトがログインを始めて利用者にリンクを開かせ、攻撃者側のセッションを承認させられると考えている（推測）。どちらもフィッシング耐性がないため、比較対象としてのみ扱い、採用候補にはしない。
