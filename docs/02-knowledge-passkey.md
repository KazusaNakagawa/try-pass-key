## 1. 試験用に作ったパスキーは普段使いに影響するか

結論として、試す分には問題ない。

- パスキーは RP ID（ドメイン）に紐づく。`localhost` 用の鍵は `localhost` でしか呼ばれず、銀行や Google など他サイトで使われることはない。
- 既存のアカウントのパスキーが書き換わったり消えたりすることもない。
- 影響は、パスワード管理画面に「localhost」のパスキーが溜まって一覧が散らかる程度である。

気をつける点は2つある。

- **終わったら削除する**。macOS はシステム設定の「パスワード」、Chrome は `chrome://password-manager` から消せる。同期されているので、1か所で消せば全端末から消える。
- **表示名に個人情報を入れない**。登録時の表示名は認証器に保存され同期される。`test-user-1` のような名前にする。

## 2. 1Password などに保存したパスキーは盗まれるか

### 結論

保管庫が開かれれば、中のパスキーも使われる。

同期型のパスキーは、秘密鍵を暗号化して保管庫に入れ、端末間で同期する仕組みである。保管庫が復号されれば秘密鍵も手に入り、攻撃者は本人として認証できる。iCloud キーチェーン、Google パスワードマネージャーも構造は同じ。

### 突破のされ方ごとのリスク

| 突破のされ方 | パスキーは使われるか | 理由 |
|---|---|---|
| 1Password のサーバー侵害 | ほぼ使われない | 保管庫はエンドツーエンド暗号化されている。解読にはマスターパスワードと Secret Key の両方が要り、サーバーはどちらも持たない |
| マスターパスワードだけ漏洩 | 新しい端末からはほぼ使われない | Secret Key も要る。ただしログイン済み端末を触られる場合は別 |
| ロック解除中の端末にマルウェア | 使われる | 現実に最も起こりうる経路。開いている保管庫から鍵を使われる、または取り出される |
| アカウント復旧の悪用 | 使われる | Emergency Kit など復旧情報の管理が弱点になる |
| フィッシングサイトへの誘導 | 使われない | ドメインが違えば鍵は呼ばれない。パスワードより確実に強い点 |

### パスワードとの比較

保管庫を突破されたときの被害はパスワードと同じ。一方で、パスキーはフィッシングで盗まれず、サーバーからの漏洩もない。総合ではパスキーのほうが安全で、1Password に保存すること自体は悪い判断ではない。

### 対策

| 立場 | 対策 |
|---|---|
| 利用者 | 重要なアカウントには端末固定の鍵（YubiKey 等のセキュリティキー、同期しない鍵）を使う。秘密鍵がハードウェアから出ないので、保管庫を突破されても盗まれない |
| 利用者 | 1Password 自体を守る。強いマスターパスワード、Emergency Kit の厳重保管、自動ロック時間の短縮 |
| サービス提供者 | 送金など高リスク操作の直前に再認証を要求する（PoC 5.3 のステップアップ認証） |
| サービス提供者 | BE/BS フラグ（同期型か）や AAGUID（どの認証器か）を見て、高リスク操作では端末固定の鍵だけを受け付ける |

PoC では AAGUID と BE/BS を記録・表示するので、1Password で登録した鍵と Touch ID で登録した鍵の違いを実際に見比べられる。

## 3. パスキー以外の方式（別PoC候補）

パスキーはログインを守るには現時点で最有力だが、唯一の正解とは限らない。PoC の脅威モデル（01 の9章）で残るリスクの多くは、ログイン後のセッションや取引承認に関するもので、パスキーとは別の仕組みが効く。

| 候補 | 何を解決するか | パスキーとの関係 | 試す価値 |
|---|---|---|---|
| ハードウェアセキュリティキー（端末固定の FIDO2 鍵）+ attestation 検証 | 同期元アカウント乗っ取りのリスク（2章）。認証器の機種を限定できる | パスキーと同じ WebAuthn。設定（attestation、BE=0 の要求）が違う | 高。本PoCの延長で試せる |
| DPoP / Device Bound Session Credentials（DBSC） | ログイン後のセッション窃取。トークンや Cookie を端末の鍵に縛り、盗んでも別端末では使えなくする | 補完関係。パスキーはログイン、こちらはセッションを守る | 高。二次被害対策に直結する |
| mTLS（クライアント証明書） | 端末そのものの認証。管理端末だけに操作を許す | 補完関係。社内システムや管理画面向け | 中。証明書の発行・失効運用も含めて学べる |
| OIDC / OAuth 2.0 で IdP に認証を委譲 | 認証を自前で持たないことによる実装ミスの削減。IdP 側でパスキーやリスクベース認証を使える | 置き換えではなく、パスキーを IdP 側に置く構成 | 中。Keycloak 等をコンテナで立てて試せる |
| 取引署名・別経路での取引確認 | 画面改ざんによる誤承認（Man-in-the-Browser）。取引内容を別端末に表示して承認させる | 補完関係。PoC 5.3 のステップアップの弱点を埋める | 中。資産を扱うなら本番では要検討 |
| リスクベース認証（端末・場所・振る舞いの変化を検知） | 正規の認証を通った不審な操作。いつもと違う操作だけ追加認証する | 補完関係。ステップアップの発動条件になる | 低〜中。データがないと効果を測りにくい |

メールのマジックリンク、SMS・TOTP のワンタイムパスワードはフィッシングに耐性がないため、比較対象としてのみ扱い、採用候補にはしない。
