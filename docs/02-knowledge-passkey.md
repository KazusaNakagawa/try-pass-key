# 調査ナレッジ: パスキーの実運用リスクと他の認証方式

- 作成日: 2026-11-23
- 位置づけ: 検討中に調べた知見の置き場。背景は [00-background.md](./00-background.md)、PoC の設計は [01-architecture-proposal-poc.md](./01-architecture-proposal-poc.md) を参照
- 表記: 「（推測）」は、仕様・公式資料・実機のどれでも裏付けを取っていない記述を表す。各社の製品の内部構成は確認していない

---

## 1. 試験用に作ったパスキーは普段使いに影響するか

結論として、試す分には問題ない。

- パスキーは RP ID（ドメイン）に紐づく。`localhost` 用の鍵は `localhost` でしか呼ばれず、銀行や Google など他サイトで使われることはない。
- 既存のアカウントのパスキーが書き換わったり消えたりすることもない。
- 影響は、パスワード管理画面に「localhost」のパスキーが溜まって一覧が散らかる程度である。

気をつける点は2つある。

- **終わったら削除する**。macOS はシステム設定の「パスワード」、Chrome は `chrome://password-manager` から消せる。同期されていれば1か所で消すと全端末から消えるはずだが、確かめていない（推測）。
- **表示名に個人情報を入れない**。登録時の表示名（`user.name` / `user.displayName`）は認証器に渡され、鍵と一緒に保存される（WebAuthn 仕様）。同期型なら他の端末にも渡ると考えられる（推測）。`test-user-1` のような名前にする。

## 2. 1Password などに保存したパスキーは盗まれるか

### 結論

保管庫が開かれれば、中のパスキーも使われる。

同期型のパスキーは、秘密鍵を端末の外（保管庫）に持ち出して端末間で同期する。そのため、保管庫を開ける者は秘密鍵を使え、本人として認証できる。ここまでは「同期する」という性質から言える。

保管庫の中で秘密鍵がどう暗号化され、どの鍵で復号されるかは各社の実装次第で、確認していない。iCloud キーチェーン、Google パスワードマネージャーも同じ構造だと考えているが、裏付けはない（推測）。

### 突破のされ方ごとのリスク

| 突破のされ方 | パスキーは使われるか | 理由 | 根拠 |
|---|---|---|---|
| 1Password のサーバー侵害 | ほぼ使われないと考えている | 1Password は保管庫をエンドツーエンド暗号化し、解読にはマスターパスワードと Secret Key の両方が要り、サーバーはどちらも持たない、と説明されている。サーバー側の実際の構成は確認できない | 推測 |
| マスターパスワードだけ漏洩 | 新しい端末からはほぼ使われないと考えている | 上と同じ前提で、Secret Key も要るはず。ログイン済み端末を触られる場合は別 | 推測 |
| ロック解除中の端末にマルウェア | 使われると考えている | 保管庫が開いている間は、鍵を使える状態にある。取り出せるかどうかは実装次第 | 推測 |
| アカウント復旧の悪用 | 使われると考えている | 復旧手段（1Password なら Emergency Kit など）で保管庫を開けられるなら、その管理が弱点になる | 推測 |
| フィッシングサイトへの誘導 | 使われない | 認証器は RP ID が一致する鍵しか使わず、サーバーは署名対象の origin を照合する。ドメインが違えば鍵は呼ばれない | WebAuthn 仕様。サーバー側の origin 照合（C3）は本PoCのテストで確認 |

### パスワードとの比較

保管庫を突破されたときの被害は、パスワードを保管庫に入れていた場合と同程度だと考えている（推測）。一方、パスキーはフィッシングで使われず（WebAuthn 仕様）、サーバーには公開鍵しか置かないので、サーバーから漏れても秘密鍵は漏れない（WebAuthn 仕様。本PoCの DB にも公開鍵しかない）。この2点から、パスキーのほうが安全で、1Password に保存すること自体は悪い判断ではないと判断している。保管庫側のリスクを比べた結果ではない。

### 対策

| 立場 | 対策 |
|---|---|
| 利用者 | 重要なアカウントには端末固定の鍵（YubiKey 等のセキュリティキー、同期しない鍵）を使う。同期しない鍵は保管庫に入らないので、保管庫を突破されても使われない。秘密鍵がハードウェアから取り出せないことは製品の説明によるもので、確認していない（推測） |
| 利用者 | 1Password 自体を守る。強いマスターパスワード、Emergency Kit の厳重保管、自動ロック時間の短縮（効果の大きさは推測） |
| サービス提供者 | 送金など高リスク操作の直前に再認証を要求する（PoC 5.3 のステップアップ認証） |
| サービス提供者 | BE/BS フラグ（同期型か）や AAGUID（どの認証器か）を見て、高リスク操作では端末固定の鍵だけを受け付ける |

PoC では AAGUID と BE/BS を記録・表示する。実機では、1Password で登録した鍵が BE/BS = 1/1、AAGUID が 1Password の値だった（[worklog 2026-11-23](./worklog/2026-11-23.md)）。Touch ID など端末固定の鍵とはまだ見比べていない。

## 3. パスキー以外の方式（別PoC候補）

パスキーはログインを守る有力な手段だと考えているが、唯一の正解とは限らない。PoC の脅威モデル（01 の9章）で残るリスクの多くは、ログイン後のセッションや取引承認に関するもので、パスキーとは別の仕組みが効く。

| 候補 | 何を解決するか | パスキーとの関係 | 試す価値（筆者の見立て） |
|---|---|---|---|
| ハードウェアセキュリティキー（端末固定の FIDO2 鍵）+ attestation 検証 | 同期元アカウント乗っ取りのリスク（2章）。認証器の機種を限定できる | パスキーと同じ WebAuthn。設定（attestation、BE=0 の要求）が違う | 高。本PoCの延長で試せる |
| DPoP / Device Bound Session Credentials（DBSC） | ログイン後のセッション窃取。トークンや Cookie を端末の鍵に縛り、盗んでも別端末では使えなくする | 補完関係。パスキーはログイン、こちらはセッションを守る | 高。二次被害対策に直結する |
| mTLS（クライアント証明書） | 端末そのものの認証。管理端末だけに操作を許す | 補完関係。社内システムや管理画面向け | 中。証明書の発行・失効運用も含めて学べる |
| OIDC / OAuth 2.0 で IdP に認証を委譲 | 認証を自前で持たないことによる実装ミスの削減。IdP 側でパスキーやリスクベース認証を使える | 置き換えではなく、パスキーを IdP 側に置く構成 | 中。Keycloak 等をコンテナで立てて試せる |
| 取引署名・別経路での取引確認 | 画面改ざんによる誤承認（Man-in-the-Browser）。取引内容を別端末に表示して承認させる | 補完関係。PoC 5.3 のステップアップの弱点を埋める | 中。資産を扱うなら本番では要検討 |
| リスクベース認証（端末・場所・振る舞いの変化を検知） | 正規の認証を通った不審な操作。いつもと違う操作だけ追加認証する | 補完関係。ステップアップの発動条件になる | 低〜中。データがないと効果を測りにくい |

メールのマジックリンク、SMS・TOTP のワンタイムパスワードは、利用者が偽サイトに入力したコードやリンクをそのまま中継されうる（origin に縛られない）。フィッシングに耐性がないため、比較対象としてのみ扱い、採用候補にはしない。
